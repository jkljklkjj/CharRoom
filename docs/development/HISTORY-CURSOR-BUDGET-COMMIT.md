# 历史游标、索引预算与合并刷盘（2026-10-30）

## 会话游标

`HistoryCursor(timestamp, id)` 表示排他边界。`IndexedHistoryJournal.pageBefore` 在有序树中直接定位较老区间，读取最多一页加一条引用判断 `hasMore`，只解码本页正文；边界行已删除也能继续。返回的 `before` 使用原始 journal 键，避免别名归并改变下一页位置。

`LocalChatHistoryStoreProvider` 新增私聊、群聊的 `get*MessagesBefore`，桌面、CLI 共用文件实现，Android 同步接入。原有按页码查询保留兼容；跨会话 `restorePage` 继续使用既有有界归并，并未改成全局事务快照。

原生聊天页上翻通过 ViewModel 在 IO 调度器读取，检查账号归属后应用。第一次根据当前最旧可见时间包含整组时间相同的记录，跳过已显示的页；后续直接沿原始游标前进。这样残留客户端 ID 经别名映射后不会改变初始时间边界。滚动观察由稳定的 `snapshotFlow` 串行消费，加载提示或用户滚动不会取消正在读取的批次，切换账号/会话仍取消观察。私聊移除了额外的最近 100 条截断；已有每会话 200 条 LRU 和全局消息缓存预算仍生效。

## 索引预算

原来的最近 64 个 journal 缓存增加 64 MiB 的估算索引预算，按访问顺序淘汰，索引增长后再次检查。估算为每个引用 `160 + 2 * ID长度` 字节，包含树/映射的保守元数据估算，不包含正文，也不是精确的 JVM 堆测量。

权重通过 volatile 数值读取，不在缓存锁内取得 journal 锁。淘汰只移除缓存强引用；弱引用登记仍确保同一路径的活跃调用共享一个 writer。正在执行的调用可以临时持有已淘汰索引，因此预算限制的是缓存保留量，不是整个进程或所有并发调用的硬内存上限。

## 单写者与合并提交

`DurableCommitQueue` 由调用线程轮流担任唯一写者，无每会话线程或永久后台执行器。写者处理当前批次时到达的请求排队；下一轮把等待请求按队列顺序合并，同 ID 保留最终修订。重叠写入可共享一次 `FileDescriptor.sync`，串行到来的请求仍及时提交，不人为延迟接收 ACK。

每个请求同步等待它所属批次的实际写入和刷盘。提交失败传回异常，后续可重试；即使失败留下了相同正文，重试仍强制刷盘，不能被空操作比较跳过。有效输入在入队前校验，原有 CRC、尾部修复、压缩和别名先落盘规则不变。

每个 journal 最多保留 256 个未完成请求、约 32 MiB 的排队/执行中内容估算，达到限制时阻塞入队；单个超过预算的既有批次可独占执行。估算包括 UTF-8 字节、原始字符串和行元数据，不限制调用方本来持有的数据。入队前中断可退出；入队后必须等到自身提交完成，再恢复中断标记，防止取消被误当作落盘成功。

接收路径仍在同步持久化返回后发接收确认；服务端发送 ACK、接收端持久化和完整历史同步游标的含义保持独立。这里优化原生文件写入，不改变后端已有的 Kafka 批量消费/MySQL 批量写入。
