# 客户端更新：下载、校验、安装与恢复

## 发布契约

后端 `V4__release_artifacts.sql` 为版本记录增加包类型、架构、字节数、SHA-256 和 APK versionCode。Web `/admin` 同步提供这些必填字段和发布确认内容；API 不再提供缺少校验信息的配置文件更新兜底，旧 `app.update.*` 已删除。

先在测试环境迁移 V4，再部署后端和 Web。已有缺失安装包元数据的发布记录不会产生更新提示；需创建并发布完整的新记录。安装包仍先上传到受控 HTTPS 存储，后台不执行下载链接或构建脚本。可用 PowerShell 的 `Get-FileHash -Algorithm SHA256` 与文件的 `Length` 获取发布数据；这些应来自最终签名后的安装包。

更新检查为 `GET /app/version/check`，参数包含 `clientVersion`、`platform`、`os`、`architecture`。后端只向匹配的操作系统/架构返回包，不把 Windows MSI 提供给 macOS 或 ARM64 设备。每个平台目前仍只有一个当前安装包，不支持同一版本的多架构/多系统并行分发；增加安装包矩阵是独立后续工作。

`gradle.properties` 的 `appVersion` / `appVersionCode` 是原生版本来源：根 Gradle 生成 `BuildReleaseVersion`，`AppConfig`、桌面包和 Android 包共同使用。生成文件不手改。Android 更新请求与安装成功判断使用实际 BuildConfig 版本；发布 APK 的 versionCode 必须高于已安装版本。

## 共享流程

`core/update/ManagedAppUpdater` 拥有独立协程作用域及状态，`UpdateHost` 位于共享应用入口，登录页和设置页都可接收提示，不再依赖设置页面保持挂载。

流程为检查 → 下载 → 校验 → 待安装 → 保存消息/草稿 → 系统安装交接。打开安装器只记录 `HandedOff`；重新启动并确认实际版本达到目标后才记录 `Completed`。强制更新禁止关闭提示，但仍需用户确认安装，不再下载完直接安装。

- 每个更新操作有代次，取消后的进度和完成结果不能覆盖新操作。任务互相取消并等待旧任务退出，避免并发写同一安装包。
- SHA-256、长度、包类型、设备架构在下载/恢复时检查；安装前再次校验，不能用下载完成标记替代完整性检查。
- 任务元数据原子落盘。被中断的下载、已校验包及安装交接可恢复；损坏元数据隔离并提示重新检查，没有旧 JSON/MD5 兼容分支。
- 保存失败或超时会阻止安装。聊天历史显式提交脏消息并 flush；私聊/群聊文本草稿按账号和类型化会话独立保存，每日回答草稿也在安装前提交。未提交附件和回复引用上下文不属于新增的文本草稿存储。
- 普通更新可稍后处理；下载取消清理任务与缓存。正常检查无更新不打扰用户，失败允许重试或重新查询已发布版本。

## 桌面

`HttpUpdateDownload` 使用 `.part`、Range 和强 ETag/If-Range 恢复下载。服务端忽略 Range 返回 200 时重新写入，不重复追加；206 范围必须准确。重定向只能保持 HTTPS，HTTP 错误页面、长度不一致、超量和摘要不匹配不会成为可安装文件。安装包按摘要命名，旧缓存有界清理，损坏缓存可在重试时重下。

Windows 使用 MSI，通过独立 PowerShell helper 等待当前进程退出，再调用 `msiexec /i ... /passive /norestart`。helper 就绪后客户端才退出，记录安装日志和退出码，再启动原应用入口。客户端退出前先保存、停止聊天连接、再次 flush。安装失败保留原版本并在下一次启动展示错误；这不是对系统安装器的跨版本自动回滚承诺。

Windows 的 MSI 和已安装启动器必须有有效且相同证书指纹的 Authenticode 签名；开发环境/未签名安装不执行自动安装。证书轮换需要单独迁移信任策略。helper 的路径通过环境变量传递，执行的脚本文本固定编码，不拼接到 shell 代码；脚本副本仅用于诊断。

macOS DMG 通过 Gatekeeper 检查后交给系统打开，Linux DEB 检查包标识后交给桌面包管理器。两者需用户完成系统安装步骤，不直接套 Windows 参数，也不承诺自动替换应用或自动重启。Linux 包完整性依赖发布元数据和 SHA-256，此实现没有为 DEB 新增发行者签名体系。

## Android

更新器在 Application 中初始化一次，仅持有 applicationContext。DownloadManager 下载任务 ID 持久化，Activity 重建不重复下载；应用重启重新连接已有系统任务。通过轮询单一任务读取状态，移除了生命周期不完整的广播接收器和 `GlobalScope`。

系统下载成功后，使用 ContentResolver 读取返回 URI，复制到应用私有更新目录并核对字节数、SHA-256。不再尝试把 content URI 转成 `_data` 文件路径。

安装前检查 APK 包名、版本名称、versionCode 及签名证书集合。当前策略要求与已安装应用同证书，不支持签名轮换。FileProvider 只分享私有 `updates/` 目录；系统安装来源未授权时打开授权页面，返回后可重试安装。启动系统安装确认界面不作为成功结果，也不尝试绕过用户确认。

## 验证与边界

自动化使用伪造 HTTP 响应、临时文件和模拟安装器，不下载或安装任何真实包。覆盖续传、Range 忽略/错误、ETag 变化、HTTPS 降级拒绝、错误页面、截断/损坏、缓存重试、平台匹配、APK 身份、安装前再次校验、保存失败、取消晚到结果、强制更新、任务恢复及版本成功确认。后台另测元数据校验和 SQL/权限，浏览器另测表单和发布流程。

2026-10-28 验证结果：JVM 117 项、Android 单元测试 5 项、后端定向测试 26 项、Web 116 项全部通过；共享 JVM/Android Kotlin 编译、Web 类型检查与生产构建、管理后台浏览器回归通过。Web 测试在并行执行遇到 Node worker 序列化错误后，使用 `--test-concurrency=1` 完整复跑通过。Windows helper 仅做 PowerShell 语法解析，未执行安装。后端本轮为定向回归，未执行全量集成测试或覆盖率验收。

跨端评估：桌面与 Android 共用更新状态、校验、恢复、提示和保存流程，安装交接按平台实现；Web 管理后台同步安装包元数据和发布确认，浏览器应用不执行原生安装器；CLI 没有新增交互式更新提示。

没有执行真实 MySQL 迁移，没有生成 JNI/APK，也没有做 Windows MSI、macOS、Linux 或 Android 真机安装。证书信任链、UAC/安装权限、MSI UpgradeCode/覆盖安装、打包后的重启路径和系统安装结果需要发布测试设备验证。没有实现差分补丁、灰度分发或自动数据降级。
